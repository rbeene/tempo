# Agent activity contract (planned v1)

This is the implementation contract for [#6](https://github.com/rbeene/tempo/issues/6) in the [agent timing epic](https://github.com/rbeene/tempo/issues/5). It specifies future behavior, not commands available in this release. [agent-operations.json](agent-operations.json) defines the shared actions and inputs; [agent-acceptance.json](agent-acceptance.json) supplies acceptance vectors. The generated [cli-schema.json](cli-schema.json) remains the authority for **shipped** commands. Each implementation ticket adds its commands to that runtime schema and corresponding tests as they ship.

CLI and UI call the same small Go operations. Activity uses one local store; appearance preferences use a separate local store with an independent revision domain. Hooks append local lifecycle evidence without network access; a separate optional worker submits completed time. Closing a UI never stops capture or that worker. This is not a plugin/event-processing framework or a new Harvest provider abstraction. Existing `time …` and `timer …` commands retain their current meanings: they operate on Harvest entries/live timers. `activity …` operates on local agent activity and never starts or stops a Harvest live timer.

## 1. Identities, scope and attribution

Each actor record also has a local `actor_id` and revision for user-directed interruption. All local opaque IDs are random UUIDs, persisted before use; Harvest IDs are canonical positive signed-64-bit decimal **strings** in the new contract. Existing Harvest response shapes are unchanged. Timestamps are UTC RFC3339 with nanosecond precision; intervals are half-open `[start,end)`, so touching endpoints do not overlap. Zero-length segments contribute zero and are not queued.

| Identity | Definition |
|---|---|
| `computer_id` | Random ID for this computer's Tempo store, not hostname, MAC address or an account ID. Stable across restarts/upgrades. A new computer gets a new ID; copying a store to another computer requires explicit migration that rekeys future capture and preserves historical IDs. No silent cloned identity. |
| timer key | `(computer_id, account_id, project_id)`. Exactly one union clock per key. Different projects/accounts/computers can overlap independently. No cross-computer/person deduplication. |
| `binding_id`, `binding_revision` | Stable identity and increasing revision of one directory/repository mapping. Deleting leaves a historical tombstone. Path labels are not identities. |
| repository locator | Canonical absolute Git common directory obtained through `git rev-parse --path-format=absolute --git-common-dir`, relative output resolved against the invocation directory and symlinks resolved. Worktrees share this locator. Do not use worktree root, remote URL, basename or scanned siblings as identity. |
| directory locator | Canonical absolute explicitly linked ordinary directory; applies to its descendants until a Git repository boundary. Longest matching directory locator wins. Inside Git, only that repository's common-directory binding applies: no inheritance from an enclosing repository or ordinary-directory link. |
| actor key | `(computer_id, source, session_id, agent_id)`, where `source` is `codex`, `claude` or `manual-test`. Session ID includes a persisted host-session incarnation; reuse after host restart without continuity creates a new incarnation. Main actor and every child have distinct agent IDs. PIDs are not stable identities. |
| generation | Strictly increasing positive integer per actor key, allocated in source execution order, not callback arrival order. One work turn; terminal generations never reopen. Serialize generation/sequence counters as decimal strings. |
| event identity | `(actor key, generation, sequence)` plus source `event_id`. Sequence starts at 1 per generation and increases by exactly 1 for each emitted lifecycle transition/evidence event. Same identity must have the same canonical payload. |
| `segment_id`, `uncertainty_id`, `interval_id`, `outbox_id` | Distinct persistent IDs for actor work, unresolved time, immutable project-union output and submission intent. Recovery targets a segment via an uncertainty ID, never just a project's opening time. |

Linking inside a Git repository always has repository-wide scope, displayed before confirmation in either interface. Outside Git it has directory scope. A separate clone or nested independent repository is unlinked until explicitly linked. Missing/relocated repositories report `binding_unavailable`; repair/relink is explicit, never inferred from a name or remote. Git discovery errors are not treated as “ordinary directory.” Stop/wait events locate the persisted actor; they do not re-resolve the current directory. A sanitized `cwd` may accompany any lifecycle event for source context; it is resolved only for initial work and never rebinds an existing generation. The first successful link initializes the local computer ID. Tracked ingress therefore already has a persisted binding/store identity; the bridge supplies that ID, and a caller-supplied different ID is rejected as `validation`. Unlinked hooks return `untracked` without creating a store or minting an ID. Engine tests may explicitly seed a synthetic identity and validated binding.

A binding contains `account_id`, authenticated `/users/me` `user_id`, `project_id`, `task_id`, and canonical IANA `timezone`. No arbitrary user override is accepted. Project/task must be active assignments for that user when linked. Timezone is supplied explicitly or taken from a previously verified saved selection; no silent machine-timezone fallback. These five fields are the **attribution tuple**. Every live binding for the same timer key must agree on user, task and timezone, even if currently idle. A mismatch returns `attribution_conflict` with safe differing field names. Different users/tasks/timezones must not become additional concurrent clocks for the same key.

An actor generation captures an immutable attribution tuple plus binding ID/revision when its first `work` is accepted. Every segment retains that snapshot. A parent-sourced child inherits the exact snapshot only when an explicit registered parent reference exists and the child has no independently linked context; an explicitly linked child uses that context and may run on a different project. An unlinked independent session is untracked. Parent relationship alone does not add activity or recursively stop children. A late child callback cannot attach to a terminal parent as a newly discovered child; child identity/context must have been registered while the parent was live, or independently resolved from an explicit link.

Relink, relocation repair and unlink reject `binding_in_use` while any generation is attached in working, waiting or stale state. A waiting actor remains attached. `activity interrupt ACTOR_ID --generation G --if-revision REV --yes` explicitly detaches a stranded generation: waiting contributes no new time; working/stale preserves its unknown tail for recovery, capped by the trusted interruption sample. It tombstones that generation without cascading to children. Project reassignment requires terminating that generation and beginning a newer one; `resume` cannot rebind it. Once detached, old segments/uncertainties/intervals/outbox records still retain their snapshots. A subsequent relink never migrates historical time. If an unresolved old attribution could overlap proposed new attribution for the same timer key, new capture returns `attribution_conflict` until that overlap is resolved. Sequential nonoverlapping attribution epochs are allowed; each epoch has its own immutable intervals. Multiple idle bindings must be changed explicitly so they agree before capture resumes; no mass rewrite.

## 2. Ordered lifecycle

The minimal ingress payload is `contract_version`, actor key, generation, sequence, event ID, `kind`, and (only for initial work) binding/parent context. Allowed kinds are `work`, `wait_user`, `wait_permission`, `wait_children`, `interrupt`, `finish`, and `observe_work`. Adapter allowlists exclude transcripts, prompts, tool arguments/results, tokens and arbitrary payload storage. Source timestamps may be retained as sanitized diagnostics but cannot backdate billing.

The engine serializes each transaction under a bounded exclusive store lock: deduplicate/order, read the fixed binding, capture its clock sample, append evidence and update materialized state atomically, then acknowledge. Failure to durably persist means no success acknowledgement. Exactly repeated events return the original effect with `disposition: duplicate`, even after restart; no interval changes. Conflicting payloads for a previously accepted identity or reused event ID return `event_conflict`. Retain accepted identity/payload fingerprints, the generation high-water mark and terminal tombstones durably; compaction may discard raw event bodies only while preserving these decisions and actor segments. Do not expire tombstones on a timer.

| Incoming evidence | Result |
|---|---|
| First `work`, sequence 1, generation greater than stored high-water (or initial generation 1) | Begin a new generation and segment at local acceptance time. A gap in generation numbers is allowed because unused allocations need not represent work. |
| Higher generation while prior generation is live | Supersede it atomically. If prior state is working, quarantine its tail as uncertainty; if waiting, there is no active tail. Tombstone the old generation as interrupted. Begin the new segment; never infer the old tail's end from replacement. |
| Exact previously accepted event | Duplicate no-op, regardless of current generation/state. |
| Unseen lower generation, or unseen event in a terminal generation | `disposition: stale`, no activity/state/attribution change. Terminal never reopens. |
| Same live generation, sequence = last accepted + 1 | Apply the transition below. |
| Same live generation, unseen sequence <= last accepted | `event_conflict`; no mutation. Exact duplicates were handled first. |
| Same live generation, sequence > last accepted + 1 | `event_gap`; do not apply or buffer the event. Quarantine any working tail, mark this generation stale and order-blocked, record the missing range. No later event of this generation automatically restores continuity. Explicit recovery is required to resolve the old gap. A higher generation may capture before recovery, while the retained uncertainty blocks overlapping/touching finalization. |
| Higher generation whose first event is not `work`/sequence 1 | `event_gap`; diagnostic only, no new generation, no effect on the current actor. |

All transitions require the ordering check first. `wait_*` states below are noncontributing but attached. “Close” means close this actor's segment, not the project clock. `stale` is a durable health flag; it is not an assertion that the agent stopped working.

| Current state | `work` | `observe_work` | `wait_*` | `interrupt` / `finish` |
|---|---|---|---|---|
| working, continuous evidence | Remain working; advance evidence, no second segment | Advance confirmed-through evidence | Close segment; enter named wait state | Close segment; detach, tombstone terminal |
| waiting | Open a **new** segment; retain generation/binding | `invalid_transition` | Change wait reason, zero activity | Detach and tombstone; zero new activity |
| stale after missing clock/liveness evidence, order intact | Open a new segment now; cap old uncertainty here, retain it unresolved | `invalid_transition`; observation cannot resume | Cap old uncertainty here; enter wait, retain uncertainty | Cap old uncertainty here; detach/tombstone, retain uncertainty |
| stale and order-blocked | `event_gap` until a higher generation | `event_gap` | `event_gap` | `event_gap`; recovery can detach explicitly |
| interrupted / finished | Stale no-op | Stale no-op | Stale no-op | Duplicate/stale no-op |

Thus `work(seq1) → wait_user(seq2) → work(seq3) → finish(seq4)` has two working segments. A replay of seq1 while waiting cannot resume. Delayed waits or stops from an older generation cannot close a newer one. A fresh `work` after finish needs a **higher generation**, never merely a higher sequence. Parent `wait_children` counts zero even with multiple/nested active children; those children independently keep their project key active. Parent finish/interrupt does not cascade. End-of-session adapters may emit individually identified terminal events only for actors for which the host actually establishes termination; unknown child endings become stale review items.

### Host bridge and sources without reliable ordered IDs

The native adapter is a small synchronous `tempo hook <host>` command registered for lifecycle callbacks. It allowlists source identifiers, durably maps them to normalized generation/event tokens **inside the callback before returning to the host**, and applies the local transaction directly. Do not enqueue raw unordered callbacks for a later worker to number. The worker is for sync, not source-event sequencing.

Codex documents `session_id`, turn-scoped `turn_id`, `tool_use_id` and child `agent_id`; subagent callbacks use the parent's session ID. Claude Code documents `session_id` and `prompt_id` (v2.1.196+), plus `tool_use_id` and subagent `agent_id`. Neither documentation establishes a universal numeric sequence or periodic heartbeat. Those are identity inputs, not a claim that lexicographic UUID order is chronology. Sources: [Codex hooks](https://developers.openai.com/codex/hooks), [Claude Code hooks](https://code.claude.com/docs/en/hooks), checked 2026-10-02.

The bounded bridge algorithm is:

1. A synchronous `UserPromptSubmit` barrier maps `(session incarnation, turn_id/prompt_id, agent_id)` to one persisted generation before work proceeds. A replay retrieves that generation; the same source turn can never acquire a second one. Subagent start similarly registers the child and inherited context. Retain source-turn/child tombstones, including a terminal callback received before its start.
2. Stable event keys combine the source turn, actor, lifecycle kind and, for tool-associated transitions, `tool_use_id`. The bridge durably allocates a normalized sequence only on first admission of a **causally admissible** transition. Pre-tool/permission/post-tool form a stored per-tool phase chain; a completed tool's delayed pre/permission event cannot rewind it. A turn terminal fences all its tool events. Parallel tool observations do not each assert actor resume/stop; only an unambiguous actor-level transition changes membership.
3. A wait-to-work transition requires a new causal edge (for example completion of the identified permission-bound tool), not replaying turn start. A source event lacking enough identity for an ambiguous repeated transition is diagnostic/review evidence only. A permission event cannot silently stop unrelated still-running child actors. A task completing is not a turn terminal.
4. The supported runtime must execute the registered start/terminal barriers synchronously in actor lifecycle order, or supply an equivalent ordered event stream. This is a capability to verify, not a guarantee inferred from the listed IDs. Synchronous capture is the useful normal path: a long start-to-stop turn closes automatically without polling the model. A new unseen turn cannot supersede a live one merely because its callback arrived later; it needs the verified source barrier/stream. A terminal received for an unseen source turn tombstones that turn, preventing a later start from opening it.
5. Callback timeout/failure, bridge persistence failure, disconnected event stream or loss of verified session continuity invalidates that source epoch. Subsequent callbacks cannot silently restore it. Quarantine affected open tails and re-establish an explicit session barrier; retain unknown history. A runtime that cannot expose/detect these conditions must advertise the affected coverage as `review_required`, not `supported`.

`Stop`/`SubagentStop` callbacks are proposals that other hooks may continue. Without a verified finality signal, normalize the callback to `wait_user` (or a known wait reason), **not `finish`**. This closes only the current work segment. A causally identified continuation opens a new segment in the same generation; the bridge records a new continuation cycle from the source barrier/ordered stream, never from `stop_hook_active` alone. A subsequent distinct prompt retires the prior waiting generation. Actual session termination/interrupt or authoritative turn completion may emit a terminal event. If the runtime cannot associate a repeated stop with its correct continuation cycle, quarantine that boundary for review rather than letting an old stop close newer work. Normal completed turns can therefore queue their closed union while the actor remains accurately “waiting for user”; stranded waiting actors can be explicitly interrupted before relinking.

If a registered generation has ambiguous intra-turn callbacks, retain its provisional range as durable uncertainty (`ordering_unavailable`) for explicit recovery; do not auto-queue it. Where even the turn/actor boundary cannot be registered reliably, retain bounded safe diagnostic observations for display but create no actor segment or recoverable timed range. `ordering_unavailable` describes this degraded coverage. Installation still provides diagnostics, but it is not complete automatic capture. #13/#14 must demonstrate barriers, retry identities, timeout handling and actual supported-runtime delivery before declaring support. No periodic heartbeat, transcript parsing, prompt hashing, agent instruction or blind daemon poll is required or accepted as lifecycle proof.

## 3. Time, missing evidence and durable history

The local computer is authoritative for capture times. The clock dependency supplies a UTC wall sample, boot/clock epoch, and comparable elapsed counters. Counters must be comparable across short-lived hook processes on the same computer/boot, survive worker restarts, and distinguish elapsed awake time from suspend time. Persist these samples with `capability: available|unavailable`; unavailable epoch/counters are null, never fabricated zero. Starting/resuming timed work without usable clock capability returns `clock_unavailable`; metadata/status reads still work and existing open time is preserved for review. UTC alone or a serialized Go `time.Time` stripped of its monotonic component cannot establish continuity. The small platform clock adapter must expose unavailable/discontinuous evidence explicitly; do not simulate continuity with wall subtraction.

Within one continuous clock epoch, chargeable duration follows elapsed time and is anchored to the first segment's UTC sample. UTC changes inconsistent with elapsed time, boot changes, suspend/resume or missing clock capability break continuity. A difference exceeding one second between wall and elapsed deltas, or between suspend-inclusive and awake deltas, is a discontinuity; tolerances and samples are persisted with the evidence. Sleep time is never automatically billed. After a discontinuity, segments use the new epoch's UTC anchor; if that would overlap incompatible or already finalized time for the key, block capture with `clock_conflict` for explicit review rather than clamp or double-count.

A working start/transition/`observe_work` establishes state at its acceptance sample. A verified source lifecycle keeps that state open until a trustworthy wait/terminal event or positive discontinuity evidence; **silence alone is neither inactivity nor missing evidence**. There is no arbitrary lease/heartbeat timeout in v1. The UI shows last-evidence age and provisional elapsed time; an open interval cannot sync. A normal 30-minute silent turn with matching ordered stop and continuous clock closes automatically. Explicit source/bridge failure, observed source-process termination without a terminal event, loss of source epoch continuity, sleep, clock change or an event gap creates uncertainty from the last confirmed evidence. Ordinary hook-command exit after a durable event is not source-process termination. A sync-worker restart does not imply source loss; restored source/clock epochs preserve an open turn. If continuity cannot be established after a store/host restart, use `restart_unknown`. No later normal stop may resolve an already recorded uncertainty. A daemon that knows only “the PID exists” cannot extend confirmed-through evidence or manufacture a work observation.

Each actor segment retains start, latest confirmed-through sample, optional reliable end, attribution, generation, accepted lifecycle references and all recovery decisions. No destructive replacement with a single project opening timestamp. On loss of continuity, split conceptually into confirmed `[start,confirmed_through)` and a durable uncertainty `U = [confirmed_through, upper_bound)`. The initial upper bound is unknown (`null`, treated as +infinity), not the detection time. A later trustworthy resume, wait, stop, generation replacement or explicit recovery observation bounds the prior segment no later than that event's acceptance time. This **caps** U without resolving it. A later clock epoch whose UTC cannot establish a valid bound requires review; it cannot create negative time.

The uncertainty record contains its own ID/revision, actor key, generation, segment ID, immutable attribution, reason (`source_lost`, `ordering_unavailable`, `suspend`, `clock_changed`, `restart_unknown`, `event_gap`, `superseded`), last confirmed sample, current upper bound and the later evidence imposing it, detection sample, and resolution/audit fields. It survives resume, new generation, finish, relink, restart and compaction. `unresolved` and `resolved` are persisted states, not labels computed only from current actor health. Pending closed time and unresolved timing are different status collections.

### Recovery and union finalization

`activity resolve UNCERTAINTY_ID` requires its current revision and either `--end UTC` or `--discard-tail`. `activity preview UNCERTAINTY_ID --end UTC|--discard-tail` is the shared read-only preview operation. It returns the uncertainty revision, original segment start/confirmed prefix, proposed end/excluded suffix, and before/after affected union ranges (plus remaining blockers), so either interface can show the same result after an actor resumes. UI shows that preview before confirming; resolve rechecks the returned revision and bounds under lock. The operation performs no Harvest writes.

- `--end E` asserts continuous work from segment start through E. Require `confirmed_through <= E <= upper_bound`, with the upper bound also no later than the recovery operation's trusted “now.” If U is still unbounded, trusted now becomes its upper bound. Respect any subsequent segment/resume/wait/terminal evidence, and reject conflicts with already finalized intervals or an incompatible attribution epoch. An end equal to the lower bound adds no uncertain time. Store the assertion and discarded suffix; do not delete the original evidence.
- `--discard-tail` retains only the confirmed prefix, explicitly discards U, and stores that decision. If this was the current stale segment with no later resumed segment, resolution detaches/tombstones that generation. Resolving an older segment does not stop a newer segment or another actor. `--end` has the same detach rule.
- Out-of-range choices return `recovery_bounds`; stale revisions return `revision_conflict`; repeating the same request ID returns its original result. An automatically received event may cap U, but **only this deliberate recovery action** resolves it. Bulk “assume stopped on crash” is not part of v1.

For each timer key and compatible attribution epoch, take the union of confirmed/resolved actor segments, merge touching or overlapping ranges, and retain the supporting segment IDs. An open working segment and every unresolved U reserve their possible range (unknown end = +infinity). A closed connected union component is finalizable only when no such reserved range intersects it **or touches an endpoint**; this prevents later evidence from extending/bridging an already finalized component. Finalize safe disconnected components separately. Finalized intervals have immutable bounds/duration/attribution and stable IDs; outbox creation is one durable transaction keyed uniquely by interval ID. Never revise a submitted interval as a consequence of later recovery. Invalid late evidence conflicting with finalized time requires review, not silent rewriting.

Example: A begins 09:00 and loses evidence; B begins 11:00 and remains working. Recover A's segment with end 10:00. A contributes `[09:00,10:00)`, B contributes only from 11:00. The interval `[10:00,11:00)` stays unbilled. When B closes at 12:00, the result is two intervals totaling two hours, not one three-hour interval. Fixture `recovery_preserves_gap` records the exact history and result.

## 4. Synchronization boundaries

Only finalizable closed intervals become `queued` outbox items; open or unresolved components cannot. Each item fixes interval ID, computer/account/user/project/task/timezone, UTC bounds, exact duration, safe notes and a unique correlation marker. Capture retains nanoseconds: day splitting/DST/account timestamp-vs-duration representation and Harvest rounding must preserve and expose residuals, never silently drop subminute time. The shipped foreground sync service implements these conversion details with isolated provider/server evidence; any unrepresentable range is `needs_attention` and not posted.

| Sync state | Meaning / allowed next action |
|---|---|
| `queued` | Durable, never attempted, or explicitly authorized conclusive rejected retry with a frozen plan; eligible for one run-lock-owned claim if sync is enabled. |
| `submitting` | Exclusive durable claim and submission intent saved **before** HTTP; no second worker can claim it. |
| `synced` | Confirmed current-user Harvest entry ID saved; immutable local interval remains. |
| `rejected` | A conclusive response establishes no entry was created; preserve item, surface auth/validation category. Retry only after explicit review/correction through `sync resolve --retry-rejected`. |
| `unknown` | Timeout, broken/invalid success response, ambiguous server failure or crash around POST/save; never automatically POST again. |
| `needs_attention` | Invalid attribution/representation or ambiguous correlation; read-only reconciliation or explicit review needed. |

Startup converts orphaned `submitting` to `unknown`, never back to `queued`. Reconciliation reads only, verifies exact current user/account and immutable interval/correlation fields, and accepts exactly one conclusive matching entry. Zero or multiple matches remain visible and blocked. A manual `sync resolve --entry ID` re-reads/verifies the selected owned entry before attachment; merely supplying an ID does not bypass matching. No “retry unknown” command in v1: lack of a read match does not prove the original write failed. Existing manual Harvest commands remain available with their own explicit uncertainty contract; they do not silently repair the outbox. Do not claim upstream exactly-once delivery without an idempotency guarantee. Stopping/pausing synchronization is independent of capture.

Explicit account/current-user mode and representation consent is saved through
`sync.configure`; no migration silently grants rounding consent. An optional expected
current-user guard rejects changed verified identity before configuration writes,
without changing historical fingerprints when omitted or bypassing saved replay. Only Company403
permits declared-mode fallback. Duration policy is exact or explicitly nearest
hundredth hour; timestamp mode is exact with declared clock and verified timezone.
All daily parts preflight before any write. Missing confirmed amounts are null;
planned and total residuals remain signed. See [commands](commands.md#safe-activity-synchronization)
for precision limits and finite controls. Terminal UI placement remains planned
for #16. The optional #12 worker uses the same sync engine and preserves this
recovery ordering; see [worker commands](commands.md#optional-automatic-sync-worker).

## 5. Shared CLI/UI operations

[agent-operations.json](agent-operations.json) is the finite v1 catalog: action ID, CLI spelling, typed inputs, result type, effects and UI placement. UIs call these actions directly and render the same state/errors; they do not shell-parse colored output, create a second timer implementation or require switching interfaces. Setup/auth/account selection, linking, hook lifecycle, recovery/sync, worker controls and themes must be complete in both. Hook preview is read-only: return normalized host/scope/path/operation intent and a deterministic SHA-256 fingerprint covering that intent, current configuration content and Tempo executable/skill version. Install/repair/uninstall resupply the intent plus fingerprint, recompute it under the configuration lock and reject drift with `revision_conflict` before changing files. No persisted random plan IDs or tracking identity are needed to move a preview between CLI/UI processes. Theme list/show return the preference revision used by UI apply/cancel flows. Existing authentication/discovery operations retain their current scopes and secure input rules. UI secret input goes directly to the same injected auth operation and is never placed in command arguments, logs or state snapshots.

`tempo link [PROJECT_ID]` resolves `--path` (default cwd). With no ID and an eligible terminal, show active assigned projects with text search, Up/Down and Enter; Escape cancels without mutation. An explicit ID skips the project picker. `--task` skips the task picker; otherwise choose a valid saved project default or the sole active assigned task, else present a task picker. Account precedence remains flag, environment, saved selection; multiple unresolved accounts require selection. Timezone is explicit or a saved verified choice. Unlinked hook paths never prompt. `--json`, `--non-interactive` or redirected input/output prohibit all pickers: missing choices produce `input_required` and safe `required_fields`, not guessed choices.

Binding edits use `link … --if-revision REV` after reading the old binding; absent revision means create-only (an identical existing mapping is a no-op). Unlink requires binding ID, revision and confirmation. Local mutations accept `--request-id UUID`; the CLI/UI creates one if omitted and keeps it stable through its own retry. Automated callers must retain/reuse it after uncertain local I/O. The store records request ID, canonical input fingerprint and result in the same durable transaction. Reuse with different input returns `request_conflict`. Entity revisions, checked under lock, protect actions based on stale UI state. A local mutation with unknown durability returns `local_write_unknown`; inspect status and retry with the **same** request ID, never a new identity. This does not authorize retry of a Harvest write. Lifecycle ingress has its own event idempotency identity instead of this flag.

New result shapes carry `contract_version: 1` inside the existing envelope `{"schema_version":1,"data":…}`. Unknown fields may be added; clients reject unsupported major contract versions. UUIDs and numeric identifiers are strings; revisions are nonnegative decimal strings. Null means unknown/absent and never zero. Lists include `[]`, not null. Status reads local state only: no credentials, Keychain prompts or network. An uninitialized store returns `computer_id: null`, revision `0` and empty collections without creating the store or minting an ID. Status never persists health transitions; it can label a newly detected discontinuity provisionally stale. A source/clock observation or event transaction must persist that quarantine before any finalization. Activity `snapshot_revision` lets UI refresh after concurrent activity-store mutations; mutations return their affected IDs/revisions. Appearance transaction revisions are separate and must never be compared with activity revisions. No streaming JSON is implied by status.

`ActivitySnapshot.project_timers` is the authoritative display projection grouped by computer/account/project. It reports provisional union and confirmed closed durations separately, with grouped actor references, unresolved IDs and queue counts. Existing `projects` retains full task/user/timezone attribution details. Both projections use the same status sample and resolved endpoints; the UI never sums actor durations or advances time itself. Live attribution compatibility and relink guards prevent conflicting overlapping attribution, and finalization rejects overlapping immutable closed intervals for a project timer. Sequential attribution epochs remain one project timer while retaining distinct accounting history. An absent store returns `project_timers: []` without creating state.

Failures with `--json` (and the new commands' `--non-interactive`) put one envelope on stderr, empty stdout, no ANSI sequences or prompts. Preserve `error.code`, safe `message`, `retryable`, `uncertain`; optional `details` contains safe field names, IDs and current revision/bounds, never secrets or upstream response bodies. Current exit meanings remain; new stable codes map as follows:

| Exit | New codes |
|---|---|
| 1 | `state_corrupt`, `clock_unavailable` |
| 2 | `input_required`, `invalid_transition`, `recovery_bounds`, `unsupported_contract` |
| 5 | `binding_unavailable`, `actor_not_found`, `uncertainty_not_found` |
| 6 | `attribution_conflict`, `binding_in_use`, `revision_conflict`, `request_conflict`, `event_conflict`, `event_gap`, `ordering_unavailable`, `clock_conflict`, `state_busy` |
| 8 | `local_write_unknown` (local durability uncertainty), `credential_write_unknown` (native credential/config effect uncertain); existing `uncertain_write` remains remote uncertainty |

`state_busy` is retryable for reads and same-ID local mutations; conflict/recovery errors are not. Exit 8 sets `uncertain: true`; other new errors set false. Existing codes/exits remain valid. Hook adapters translate errors to host-required success/output/deadline behavior so capture failure does not block agent execution; safe Tempo diagnostics still retain the failed category.

### Appearance preference transactions

Theme list/show expose `preference_revision` and persisted selection without writes; an absent preference store means `terminal-default` at revision `"0"` and creates no tracking identity. `themes show ID` reports `selected` exactly when that ID equals the saved selection. Preview/cancel changes no persisted data.

For `themes.set` and `themes.reset` only, `MutationResult.snapshot_revision` is the preference-store transaction revision, independent of activity. Each first-admitted successful request records one receipt and advances that transaction revision once, including a selection no-op. `changed` describes only selection change; `entity_revision` is always the resulting preference revision, and `affected_ids` is `[]`. Preference revision advances only when the selected ID changes. An initial default no-op can therefore return transaction revision `"1"`, preference revision `"0"` and `changed: false` without creating activity state.

Reset normalizes to Set `terminal-default` before fingerprinting and never deletes receipts or resets counters. For a known request ID, compare canonical intent before checking the current revision: exact replay returns the original result after re-synchronizing durability, advances neither counter and never reapplies an old selection. Changed intent returns `request_conflict`. Omitted and explicit revisions are distinct intent inputs; output flags are not. For a new request ID, check a supplied preference revision even for a no-op. A stale apply returns `revision_conflict`; unknown durability retains the exact request ID/intent for same-ID retry.

Replay results describe historical transactions. UI rereads list/show after replay to display current saved selection. A draft keeps its originally observed revision through refresh; conflict requires a fresh deliberate Apply, never silent revision substitution. Cancel does not undo another writer or an in-flight commit. Preferences share one atomic durability boundary with their typed receipts and remain separate from authentication, activity and terminal-emulator settings.

### Terminal selection and lifetime

| Invocation | Both stdin/stdout TTY, no forcing flags | Either stream redirected, or `--json` / `--non-interactive` |
|---|---|---|
| `tempo` (no command) | Dashboard | Finite local activity snapshot; redirected/forced mode emits the JSON envelope |
| `tempo ui` | Dashboard | Finite local activity snapshot |
| `tempo activity status` | Finite human-readable snapshot | Finite JSON snapshot |
| `tempo activity status --watch` | Interactive refresh view | Finite JSON snapshot; flags/redirection override watch |
| `tempo link` / `tempo setup` | Interactive missing-input flow | Finite result or structured `input_required`; never read a secret/picker input implicitly |

There is **no `tempo status` alias**. Use `tempo activity status --json` for local state; `tempo timer status --json` remains Harvest state. `help`, `schema`, `version` remain offline finite commands regardless of terminal state. Explicit `auth login --token-stdin` still reads its declared bounded input and is not an implicit prompt.

Choose the mode before applying deadlines or touching terminal state. Finite commands retain the two-minute overall deadline and 30-second maximum HTTP attempt. Intentional dashboard/watch sessions have a signal-cancellable lifetime without the command-wide two-minute timeout; each refresh has a 250 ms maximum local lock wait, each other local lock acquisition a 1 second maximum, and each network/setup operation its own finite command deadline. A failed refresh shows the last snapshot as stale with a safe error, never resets counters. Hooks acquire the local lock within 250 ms, perform no network, and must finish within a 1 second internal budget (or a shorter documented host deadline); deadline failure must not be acknowledged as persisted capture.

One owner saves/restores raw mode, alternate screen, cursor and color state. Run shutdown/cleanup to completion **before** `os.Exit`; a `defer` in `main` that calls `os.Exit` directly is insufficient. Handle raw-mode Ctrl-C as a key as well as OS SIGINT, SIGTERM, EOF, render/write/read failure, `q` and Escape cancellation. Cancel refresh/action workers, release locks, restore terminal, then return exit: q/Escape/EOF = 0; Ctrl-C/SIGINT = 130; SIGTERM = 143; I/O error = 1 with a safe diagnostic after restoration. Escape in a picker returns to the previous view or cancels a standalone command; it never commits preview state. A dispatched mutation with no conclusive reply retains its uncertainty code and exit 8 even when cancellation caused shutdown; signal exits never hide potentially applied writes. Terminal cleanup does not terminate actors or suspend synchronization. Sanitize control/escape sequences in dynamic labels and paths before rendering; JSON preserves safe data without presentation escapes.

## 6. Implementation acceptance

The machine vectors are acceptance inputs and expected observations, not claims that the feature already passes. They require a future implementation test driver. No reference production engine or pretend file-existence tests are introduced here. Fixtures use short, explicitly supplied clock/evidence samples; the long recovery example supplies an explicit source-loss event. Consumers must test durable restart behavior against real storage and process boundaries, not only an in-memory reducer.

Required independent checks: ordered transitions/replay after restart; parent/nested actor union; parallel projects/computers; precise recovery bounds and preserved gap; uncertainty after resume/replacement/normal stop; mapping conflicts and worktree discovery; clock/sleep/source-loss evidence; simultaneous store writers and outbox claims; no credentials/network for local status; and PTY selection/restoration. Runtime adapters additionally need official-payload and real supported-host smoke evidence. Synchronization additionally needs mock-server ambiguous-write/reconciliation tests. None of these permit personal credentials, real Harvest mutations, personal agent settings changes, Titan or AWS operations.

### Shipped guided authentication boundary

Setup and direct auth commands use the same bounded native helper and account-selection operations. Authentication/config writes serialize across the per-user credential namespace; a dispatched helper write with no conclusive reply has unknown effects even after the helper is killed and reaped. `credential_write_unknown` is nonretryable and carries safe `details.effects` for credential/config. Inspect status and config before an explicit replacement; no automatic replay or credential rollback is implied. Guided setup confirms authentication and linking as separate steps; `error.details.completed_steps` and human diagnostics preserve earlier completion when a later step fails. Finite setup and default doctor only inspect local account configuration/bindings and known capability limits.
